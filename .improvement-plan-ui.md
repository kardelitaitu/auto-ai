# High-Performance Non-Intrusive UI Integration Plan

The current implementation of the UI (`api/ui/electron-dashboard/dashboard.js`) is technically "optional," but **architecturally intrusive**. 

Currently, `Orchestrator.startDashboard()` initializes an `Express.js` web server and a `Socket.io` WebSocket server directly within the main `node` process orchestrating playright browsers.

While the CPU load for polling every 2 seconds is low, maintaining open WebSocket connections and Express HTTP routers inside the core automation loop strictly violates our philosophy of **Zero-Overhead Orchestration**.

## Core Problem: The Event Loop Tax
Every time a user connects to the dashboard, `Socket.io` processes network packets on the **exact same Node.js Event Loop** that is racing to allocate Playwright `BrowserContexts` and dispatch async API tasks. This introduces uncontrollable micro-stutters during heavy loads.

---

## 🚀 The Plan: 100% Non-Intrusive Decoupling

To make the UI genuinely invisible to the core API's performance, we must isolate it completely into a separate hardware thread / OS process.

### Step 1: Child Process Isolation
Instead of `new DashboardServer()` running natively in the Orchestrator, the Orchestrator will spawn it as an asynchronous detached **Child Process** via Node's native `child_process.fork()`.

### Step 2: Zero-Blocking IPC (Inter-Process Communication)
The Orchestrator will no longer run `express` or `socket.io`. Instead, every 2000ms, it will fire a blazing-fast native IPC message:
```javascript
// Inside Orchestrator (Main Process)
if (this.dashboardProcess) {
    this.dashboardProcess.send({
        type: 'metrics_tick',
        payload: { sessions, queue, metrics }
    });
}
```
This takes `< 0.1ms` of event-loop time.

### Step 3: The Dashboard Server (Child Process)
The `api/ui/electron-dashboard/dashboard.js` file will be refactored to:
1. Listen for `process.on('message')` from the parent Orchestrator.
2. Run the `Express` and `Socket.io` servers entirely on its own CPU core.
3. Broadcast the incoming IPC payloads over WebSockets to the Electron Frontend.

### Step 4: The Electron Frontend (Renderer)
The renderer remains entirely unchanged. It will continue connecting to `ws://localhost:3001`. It will have absolutely no idea that the backend WebSocket server was successfully migrated off the Orchestrator's main thread.

---

## Benefits of this Architecture:
1. **Zero HTTP/WebSocket Overhead**: Network traffic hitting port 3001 cannot stutter or freeze the Orchestrator.
2. **Crash Resilience**: If the Electron UI or Socket.io server crashes (e.g., from an out-of-memory buffer or flood of reconnections), the core Orchestrator **will not crash**. It will simply lose its IPC pipe.
3. **True Separation of Concerns**: Automation scales independently of the Observability layer.
