# API Architecture & Performance Improvement Plan (Phase 2 - Speed & Responsiveness Focused)

Based on the requirement that runners only live for 10-minute sprints using anti-detect proxy browsers, long-term concerns (like log rotation or rate-limiting) are irrelevant. 
**The absolute priority is squeezing every millisecond of responsiveness out of the Node.js event thread and keeping the RAM footprint flat during that 10-minute window.**

Here is the brutal, highly targeted improvement plan:

## 1. Eliminate the Playwright Page Pool (Renderer Memory Leaks)
**The Problem:**
`SessionManager.js` uses a `pagePool` that keeps `page` objects open and endlessly reuses them across different tasks to "save time." However:
1. Playwright renderer processes leak DOM nodes and JS heap memory when a single page navigates continuously without resetting.
2. In `api/core/init.js`, initialization functions like `blockDialogs` call `page.on('dialog', ...)` and `lite` mode calls `page.route('**/*', ...)`. Because the page is reused, these listeners are **stacked on top of each other every single task**. After 5 minutes, you might have hundreds of overlapping listeners triggering simultaneously on a single page, crippling responsiveness.

**The Fix:**
- Rip out `pagePool` entirely from `SessionManager.js`.
- Alter `acquirePage` to just call the lightning-fast `await context.newPage()` to spawn a clean slate.
- Alter `releasePage` to aggressively call `await page.close()` to nuke the renderer memory immediately.
- *Result: Zero memory leaks, zero event listener stacking, and perfectly flat RAM usage for the entire 10-minute run.*

## 2. Eliminate Recursive Task I/O (Module Caching)
**The Problem:**
Every time a task executes, `Orchestrator._importTaskModule(taskName)` fires. This function relies on iterating over 4 different relative file paths and `try/catch` catching the OS "Module not found" error until it hits the right one. Worse, if they all fail, it dynamically imports `fs/promises`, reads the entire `tasks/` directory from the hard drive, and does case-insensitive string matching. Doing this continuous disk scanning for *every single task* under high concurrency introduces harsh CPU/IO bottlenecks.

**The Fix:**
- Inject an `Map` cache (`this.taskModuleCache`) into the Orchestrator.
- Once a task module (like `followback.js`) is successfully resolved from disk the first time, store the loaded module directly in memory.
- *Result: Disk I/O for task loading drops to absolute zero after the first millisecond, drastically speeding up task ignition.*

## 3. Nuke Proactive Background Polling (`Automator.js`)
**The Problem:**
Since the runner is a short-lived 10-minute tactical strike, it doesn't need to behave like a 24/7 web server. Currently, `Automator.js` runs proactive intervals (`startHealthChecks`), occasionally firing Axios background requests (`checkNetworkConnectivity`) and testing CDP connections just to see if the proxy is still alive. This is unnecessary background HTTP noise that steals CPU ticks from actual tasks.

**The Fix:**
- Strip out the proactive interval polling (`setInterval`) from `Automator.startHealthChecks`. 
- Rely 100% on Playwright's native event-driven `browser.on('disconnected')` to immediately and reactively kill dead sessions. 
- *Result: The Node.js event loop gets completely freed up to focus entirely on blasting through the `AsyncQueue` without background polling interruptions.*


## Phase 4: Extreme Throughput & Stability (Tomorrow's Agenda)

### 1. Asynchronous Log Flushing & Rotation (`logger.js`)
**The Problem:** 
- `LOG_BUFFER` flushes every 1 second by running a synchronous `Array.map` over thousands of JSON objects, causing major Garbage Collection pauses and micro-stutters in the Node event loop.
- Logs simply append forever into `logs.txt` and `logs.json`. At scale, this guarantees a production disk crash.

**The Fix:**
- Transition log processing from a synchronous bulk array to a non-blocking readable stream write, or offload it entirely.
- Implement daily or size-based log file rotation (max 10MB per file) and purge old logs.

### 2. Kill the 2-Second Task Stagger (`orchestrator.js`)
**The Problem:**
- The `taskStaggerDelayMs = 2000` artificially throttles queue execution by adding 2 massive seconds of dead-time between every dispatched task start. A burst of 30 tasks forces the 30th task to wait a full minute just to boot up.

**The Fix:**
- Rip out the hardcoded sleep delay.
- Replace it with a modern Sliding Window Rate Limiter or Dynamic Concurrency model (only throttle if CPU > 80% or network degrades).

### 3. Eliminate Extraneous CDP Round-Trips (`checkPageResponsive`)
**The Problem:**
- A proactive health check fires an `await page.evaluate(() => document.readyState)` across the CDP protocol before *every single task starts*. This injects a constant latency tax across the entire API.

**The Fix:**
- Eliminate proactive `readyState` validation immediately before task kickoff.
- Fallback entirely to existing timeout boundaries in the queue wrapper and standard Playwright navigation error events. This makes task startup instantaneous.
